# Search design (static inverted index in R2)

**Goal**: full-text search over all books (base text first, then commentary) with no D1 writes and tiny Worker CPU. Notes stay in D1 (unchanged). The old D1 `segments LIKE` search remains as fallback when `search/manifest.json` does not exist (or `?legacy=1`).

## Pipeline (`.github/workflows/search_index.yml`, manual)
1. `plan` – lists books without `search/_partial/<book-id>.json.gz` in R2 (`force` rebuilds; `extra` also adds non-Sefaria books found in `catalog/*.json`).
2. `partial` (matrix, `max-parallel: 2`, resumable) – builds the section files with the same `import_export.py` code as the site (so segment indexes are identical), then `build_search_index.py partial` -> one gzip JSON per book (term -> delta-coded local segment ids; commentary term -> (segment, commentator)). Non-Sefaria books: `fetch-r2` downloads their section files at ~3 req/s (Cloudflare REST limit), then the same `partial`.
3. `merge` – downloads all partials (1 REST GET per book), assigns global segment ids (books sorted by id => each category is a contiguous id range), writes `search/v<stamp>/**.bin` shards and finally `search/manifest.json` (switch is atomic; old versions can be deleted later). Upload: `scripts/upload_search.py --threads 2` (thin wrapper around `upload_r2.call`, because `upload_r2.py` only uploads `*.json`).
Adding a book later = run the workflow again (only the new partial is built, merge rebuilds shards from all partials).

## Normalisation (identical in Python `build_search_index.py` and `worker/search.js`)
strip HTML tags -> delete nikud/cantillation (U+0591–05BD, 05BF, 05C1/2/4/5/7), `" ' ׳ ״` and ZWJ -> fold final letters (ך ם ן ף ץ) -> every other non-Hebrew-letter char is a separator (maqaf, punctuation, Latin, digits). Words of 2–24 letters are indexed.

## Index files (R2)
- `search/manifest.json` (~100–500 KB): `v`, `cm` (commentator multiplier, power of 2), `who[{id,name,he}]`, `books[{id,lo,hi,secs[],n[]}]` (section names + segment counts => global segment id <-> book/sec/idx), `split{family:[keys]}`.
- Global segment id (gid) = id of a **base-text segment** (verse / mishnah / Gemara segment). Commentary hits point to the base segment they comment on, with the commentator: `value = gid*cm + commentatorId`.
- Four families under `search/v<stamp>/`, each stored as a few ~16 MB **pack files** `<family>/p<N>.bin` plus `<family>.loc.json` (`shard key -> [pack, offset, length]`); the Worker reads a shard with an R2 range request. (First attempt uploaded ~5 000 single shard objects through the REST API; it stalled at ~2 900 because of the account-wide request limit, hence packs: ~100 objects per version.): `b` (base words), `bx` (base, prefix-expanded), `c` (commentary), `cx`. `x` families index every word under itself **and** with 1 or 2 leading prefix letters ו ה ב כ ל מ ש removed (remainder ≥ 2 letters), so "ignore prefixes" is a single lookup (query `שמים` also finds `ושמים`, `בשמים`, `והשמים`).
- Shard (a logical unit inside a pack) = first 2 letters of the term (22 letters -> `a..v`, e.g. `ab.bin`); a 2-letter key whose shard exceeds ~300 KB is split by 3 letters (`split`, 2-letter terms go to `xy_.bin`).
- `.bin` layout (little endian): `TWS1`, u32 nTerms, u32 dictBytes, dictionary (terms as bytes 1..22, NUL-terminated, sorted), u32 offsets[nTerms+1], postings. A posting list = varint count; if ≤128: first value + varint deltas; else skip table (per 128-block: delta of first value, byte length) followed by the blocks (varint deltas). The Worker never decodes a whole big list: it leap-frogs (rarest term first, `seek` through the skip table).

## Query (`worker/search.js`, called by `/api/search`)
Params: `q` (`"…"` or `phrase=1` = exact phrase), `pref=1`, `layer=base|comm|all` (all = base first, then commentary), `book=id,id`, `cat=tanakh,…`, `who=Rashi,…`, `limit`≤30, `after=<cursor>`, `legacy=1`. Steps: manifest (cached in the isolate 5 min) -> fetch one shard per query word (isolate LRU cache 48 MB) -> leap-frog intersection in gid order restricted to the book/category ranges (+ commentator filter) -> candidates are verified against the real section JSON from R2 (`env.R2.get`, no REST limit; exact phrase = adjacent words, prefix option = same rule as the index) and a highlighted snippet (`<mark>`) is made. Results are in reading order; cursor `b:<value>`/`c:<value>` gives "more results". Verification caps: 14 section files and 4000 candidates per request (response has `more:true` and a cursor if it stopped early).

## Size / time / limits (measured)
- **All 808 books** (core Sefaria + every `catalog/*.json` book; built 2026-11-27): 793 872 base segments, 247 commentators (cm=256, auto-grows to 512 when exceeded). Index **471.6 MB** = b 75.9, bx 111.6, c 114.7, cx 169.3 MB, in 35 pack objects + loc maps; manifest 808 KB. R2 free tier is 10 GB. (First 139-book build: 200.7 MB.)
- Build: partial jobs are matrix jobs (core books one per job; the other ~670 books in 23 batch jobs of 30, reading `packs/<book>/index.json` = a few big GETs per book, ~1 min per batch, ~45 min total wall with max-parallel 2). Merge 4.7 min (≈4 GB RAM, one partial in memory at a time), upload of ~450 MB in ~35 PUTs ≈ 5–10 min. REST downloads of the 808 partials: use `fetch-partials --threads 8` (single GETs sometimes stall; the Actions merge job hung on this twice, so merge+upload can also be run from any machine with the API token: `fetch-partials`, `merge`, `upload_search.py`).
- **Live latency** (curl from a cloud container, workers.dev): warm 0.25–0.55 s total (server-side 55–300 ms) for typical queries; 10 hits from 10–15 different section files 0.5–0.9 s; cold isolate 1.1–1.4 s (manifest 808 KB + loc maps + first shards). Per family (all return hits): Tanakh, Halakhah (Mishneh Torah phrase → Foundations of the Torah 1:1), Yerushalmi, Tosefta, Midrash, Responsa, Chasidut, Kabbalah, Musar, Jewish thought, Second Temple, Liturgy (phrase "ברוך אתה"), commentary filter (Rashi).
- **CPU**: Worker CPU per request is not exposed to the client. Wall time is mostly R2 I/O. Expected CPU: cold start ≈ JSON.parse of the 808 KB manifest + building 79 k-entry lookup arrays (≈ 8–12 ms), warm request ≈ 2–6 ms for 1–3 section files and 10–25 ms for 10+ big Bavli/commentary sections. The free-plan limit (10 ms) can therefore be exceeded on cold starts and result-heavy queries; mitigations: default `limit=5`, trimming the manifest (drop `title`, compress section names), or the paid plan ($5/month, 30 s CPU). Check the Workers dashboard (CPU time p50/p99) after real traffic.
- Limits: no ranking (reading order: Tanakh, Mishnah, Bavli, Yerushalmi, Tosefta, Midrash, Halakhah, Responsa, Kabbalah, Chasidut, Musar, Jewish thought, Liturgy, Second Temple; alphabetical by book id inside a category); no fuzzy/morphological search beyond the 7 prefixes; 1-letter words are not indexed (still verified inside phrases; a phrase with `ה'` for the divine name is not matched because texts spell it differently); commentary hit = same commentator + all words in one comment; a query whose candidates all fail verification returns `more:true` with few/no hits (candidate/section budget per request: 4000 / 14).
- Incremental updates: push a change to `.github/search_run.txt` on `search-work` (contains `extra` to include catalog books, `force` to rebuild all partials), or dispatch the workflow once it is on `main`; only missing partials are built; merge writes a new `v<stamp>`; delete old `search/v*` prefixes later (the stalled first version `search/v20261126221942` still holds ~2 870 tiny files).
